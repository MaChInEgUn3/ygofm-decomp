# PsyQ SDK and hand-written assembly functions, with the names
# krystalgamer's tree gives them (config/slus_01411/functions.csv, rows
# marked sdk_asm or handwritten_asm). Format: func_ADDR<TAB>Name<TAB>kind<TAB>lib
#
# Why this file exists: on 2026-09-08 krystalgamer described the wall his
# agents keep hitting -- they re-derive struct and argument types from m2c's
# guesses instead of using the real SDK definition, and then permute against
# a shape that cannot match. His example was func_80085DB0 = GsClearOt, where
# the pointer is a GsOT * and the record is 0x14 bytes. Reading the real name
# off this table costs one grep and settles the argument list.
#
# It is a POINTER, not evidence: the name is his identification, and what
# decides a candidate here is still the build. But a named callee tells you
# the argument count and the types, which is exactly what m2c invents.
#
# Our docs/LIBRARY_FUNCS.txt stays as it is -- a bare list of names that four
# tools parse line by line -- because adding a column to it would break them.
#
# WHAT THE IMPORT MEASURED, 2026-09-08 (355 named rows, all sdk_asm):
#  * 229 of them are already in our docs/LIBRARY_FUNCS.txt;
#  * 126 are NOT -- and 28 of those 126 are byte-exact C in our src/. So the
#    two "out of scope" lists disagree, and the disagreement is informative
#    rather than an error: an sdk_asm row means "he keeps it as assembly",
#    not "no C reproduces it". 29 of the 355 are matched here in total.
#  * 98 named functions are still assembly on both sides -- that is the pool
#    where a name buys the most, because it is where a candidate would
#    otherwise be written against m2c's invented prototypes.
#  * exactly ONE function is in both our LIBRARY_FUNCS.txt and our src/
#    (func_80082780), which is a real contradiction in our own file and is
#    worth a look before that list is trusted as a filter.
#  * only 3 of the 355 sit below the 0x80073840 boundary this project uses
#    to define library code, so the boundary is close to right.
