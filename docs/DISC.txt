The retail disc, and the 24 addresses that are not in the executable
====================================================================

Written 2026-08-21, the day the CloneCD image (`YUGIOH.ccd`/`.img`/`.sub`)
was put in the repo root. `.gitignore` covers `*.ccd`/`*.img`/`*.sub` and
`/extracted/`; the disc is copyrighted and must never be committed. Re-derive
everything below with `.venv/bin/python tools_src/disc.py`.

The question this answers
-------------------------
`config/undefined_funcs_auto.txt` lists 24 addresses the game `jal`s into that
have no listing in `asm/nonmatchings/`, in two tight clusters plus one outlier:

    0x801680F4 .. 0x8016AA6C    11 functions
    0x8018001C .. 0x80183FE4    12 functions
    0x801462B0                   1 function

The natural reading is CD overlays -- FM swapping code per game mode -- and the
natural next step is a second splat target. Both were checked before spending
anything on either.

What the disc actually contains
-------------------------------
Nine entries. No `.OVL`, no second executable, no `PS-X EXE` header outside
`SLUS_014.11`:

    SLUS_014.11             1,902,592
    SYSTEM.CNF                     68
    DATA/MODEL.MRG        351,019,008
    DATA/WA_MRG.MRG        37,748,736
    DATA/MOVIE.STR         35,430,400
    DATA/SD_BGM.DAT        14,675,968
    DATA/MASTER.XA          5,742,592
    DATA/SU.MRG             2,537,472
    DATA/SD_SE.DAT          1,521,664

`disc.py` measures MIPS density as `jr $ra` occurrences per megabyte, against
the executable's own `.text` as the reference -- the reference is the point,
because "looks like data" means nothing without a number for what code looks
like on this same disc:

    SLUS_014.11 .text        3788 per MB     <- reference
    SLUS_014.11 whole file   1026 per MB     (diluted by data and zero fill)
    MODEL.MRG                  44 per MB
    SU.MRG                     18 per MB
    every other file            0 per MB

So there is **no uncompressed MIPS code anywhere on the disc outside
`SLUS_014.11`**. The 44 and 18 are structure noise, two orders of magnitude
below code.

Three things this falsified
---------------------------
1. **"The bytes are not here."** They were not, until the disc arrived. This
   entry exists partly because that answer was given without asking whether
   the image could be supplied -- it could, and was, in one message.

2. **"The code is in the executable's data section, just typed as data."** A
   good hypothesis and wrong. Every one of the 24 addresses maps inside the
   `carddata` segment's file range, and every one reads as `00000000`. The
   whole segment is 9.7% non-zero and contains 0 `jr $ra` and 0 stack
   prologues.

3. **A comment in `config/SLUS_014.11.yaml`.** It claimed one dense ~188 KB
   block at vram `801ab728-801d9728`, "very likely the card database". That
   address has ONE non-zero byte in the next 188 KB. The real dense content is
   three blocks at the end of the file -- 8 KB at `8020f728`, **116 KB at
   `80213728`**, 20 KB at `80237728`, at 68/87/88% non-zero. The density
   figure in the old comment was right and the address was off by 0x68000,
   which is the signature of a number that was reasoned about rather than
   measured. Corrected in place.

   RESOLVED 2026-09-01, and the guess was wrong in a useful way: the 116 KB
   block is the game's TEXT blob (all 722 card names, the 24 type names and
   the 10 guardian-star names, 0xFF-delimited, in the custom 1-byte encoding
   Data Crystal publishes as a .tbl), and the 20 KB block beside it is the
   card STATS table -- 722 packed u32s at file 0x1C4A44 (= vram 0x801D4244
   under the plain file+0x8000F800 formula): ATK bits 0-8 x10, DEF bits 9-17
   x10, guardian stars bits 18-25, type bits 26-30. Decoded and verified on
   Blue-Eyes, Dark Magician, Kuriboh and card 722. The PS-X header's
   t_addr/t_size (0x80010000, 0x1D0000) describe ONE linear load, which is
   what makes that formula hold here.

   OPEN, and it is a build-config question, not a doc one: config/
   SLUS_014.11.yaml gives the `carddata` segment an explicit vram override
   (0x800fe728, "vram jumps past the bss gap") that contradicts the linear
   header. The build still hashes because splat emits the bytes in file
   order whatever it labels them -- but it means splat's own asm/data dump
   for this region may carry the wrong vram, which is exactly why a first
   read of D_801D4244 through the yaml came back as zeros. Verify the
   override against the header before trusting any symbol splat placed in
   this segment; fixing it means re-splitting and re-checking the hash.

What is established about the 24 addresses
------------------------------------------
* The `jal`s are real, not a splat artefact. `func_80043960` at 0x80043AFC
  encodes `0C05A03D`, which is `jal 0x801680F4` and nothing else. **20 of the
  24 have at least one caller already in `src/`** -- that is, in a function
  that reproduces the retail bytes exactly, so the call is in the shipped code
  and not in something we mis-split.
* Their target region is all-zero on disc.
* `D_800101D8`, a `u8 *` in rodata, **equals 0x80168000**, and five display-list
  functions (`func_8003B808`, `func_8003BA14`, `func_8003BD14`, `func_8003BF00`,
  `func_80043328`) use it as a *buffer* pointer.

That last point is the interesting one: the same address is both a call target
and a GPU work buffer. Overlay RAM being recycled as a buffer once the overlay
is done is ordinary PS1 practice, so this is consistent -- but it is
consistency, not proof.

What is NOT established
-----------------------
Where the code comes from. The live hypothesis is a **compressed** overlay
inside one of the archives, most likely `SU.MRG` (2.5 MB, the only small one)
or `WA_MRG.MRG`. `disc.py` cannot see that by construction: a packed overlay is
indistinguishable from data by an instruction-pattern metric. **Do not read a
low density as "no code here" -- read it as "no code here in a form this
measures".**

Also unestablished: whether anything is *swapped*. Two clusters is not
per-screen overlays. Two auxiliary modules resident for the whole run produce
the identical signature.

What it would take, and why it is not next
------------------------------------------
(a) find which archive holds it, (b) work out the container format and any
compression, (c) extract exact bytes, (d) build something that reproduces
them. (a) to (c) is ordinary reverse engineering. (d) is the one that decides
whether the work is real: this project rests entirely on `build.py` producing
one file whose sha1 either matches or does not, and every rule in WORKFLOW.md
is there because it survived that comparator. A second target with no
byte-exact reference produces C that is plausible and indistinguishable from
C that is correct -- which is the exact failure mode this repo documents over
and over.

And the decompressor, if there is one, is in the main executable, probably
among the functions still in assembly. So the path to the overlays runs
*through* the current scope, not around it. Nothing in the remaining in-scope
work is blocked on any of this; it is additive scope for later, not an
obstacle now.


RESOLVED 2026-08-30: it is /DATA/WA_MRG.MRG, and it is not compressed
--------------------------------------------------------------------
A second decompilation of this executable (Unchiga's, shared as a zip on
2026-08-30) had already found it, and the finding survived the only test that
matters here: his extractor, run against OUR OWN `YUGIOH.img`, produces a
90,112-byte image whose sha1 is
`77b6430db58439e9577533d4f4fa2762996cf6fc` -- byte-identical to the copy he
shipped. Two discs, one extractor, the same bytes. The tool is installed as
`tools_src/extract_overlay.py` with its provenance in the docstring; the
output is gitignored by the existing `*.bin` rule.

    /DATA/WA_MRG.MRG, LBA 10102, 37,748,736 bytes
    seven identical raw copies at LBA 16072 + n*235
    resident image 0x80146000-0x8015C000, 0x16000 bytes
    the loader is case 7 of func_800171A8 (still assembly here, and in
    candidates.py's own dup-%hi list)

Three of the four steps above are therefore closed, and the fourth -- "build
something that reproduces them" -- has an oracle now, which was the whole
objection. What is NOT closed is where overlay work belongs: it cannot be a
segment of `config/slus01411.yaml`, because the EXE's own bytes at
0x80146000 are zero (90,112 bytes, one stray non-zero byte). Attaching it to
the main oracle would make a build emitting CORRECT overlay code go red and
one emitting zeros stay green. It needs its own target, its own asm tree and
its own hash check, exactly as `sha1 84747e64...` works for the main image.

Two corrections to what stood above.

The compression hypothesis was wrong. The image is raw. The reason
`tools_src/disc.py` did not see it is not that it was packed: it is that
disc.py measures instruction density over whole archives, and this is 90 KB
of code inside a 36 MB file. The warning in the previous section -- "do not
read a low density as 'no code here', read it as 'no code here in a form this
measures'" -- was the right instinct pointed at the wrong mechanism. A
per-sector scan would have found it; a per-archive average never could.

And `0x801462B0`, listed above as the lone outlier among the 24 undefined
call targets, is inside the overlay. It is not an outlier. It is the first
piece of evidence for exactly this, and it was sitting in
`config/undefined_funcs_auto.txt` the whole time -- func_8001BAF0, decompiled
here on 2026-08-29, `jal`s straight into it.
